# v0.2.2 app review

Reviewed: 2026-06-02

Scope: current `codex/v0.2.2-intune-chat` worktree, desktop renderer, Electron main/preload, runtime Graph/MSAL/LLM adapters, SQLite Intune Chat cache, onboarding/settings/agent/chat user flows, and a live Microsoft Graph spot check through Lokka MCP.

## Overall assessment

v0.2.2 is directionally right. Intune Chat now feels like a real operating surface beside Agents, the SQLite cache is in the correct process, the local self-training feature is opt-in and approval-gated, and the Graph PM tests catch endpoint/property drift. The current state is suitable for internal test driving.

It is not yet a release candidate. The remaining gaps are mostly correctness and trust hardening: chat needs more deterministic operators for common Intune questions, IPC should move from TypeScript-only trust to runtime schemas, and Electron should be hardened to the security checklist before shipping.

## Priority 0 before release

### 1. Page through Graph cache resources

Current state: addressed in the worktree. `refreshGraphCacheInternal()` now follows `@odata.nextLink` up to a bounded cap and stores row count, page count, and cap status in SQLite.

Why it matters: live spot checks returned `@odata.nextLink` for managed devices, Entra devices, groups, sign-ins, directory audits, and remediation scripts. The chat cache can currently present page-one data as if it represents the tenant.

Remaining work: tune per-resource caps after live-tenant pilot testing and add a richer source details drawer for completed messages.

Evidence:
- `apps/desktop/electron/state.ts` `refreshGraphCacheInternal()`
- `apps/desktop/electron/intune-chat/sqlite-store.ts` `replaceGraphResources()`
- Microsoft Graph paging guidance: https://learn.microsoft.com/en-us/graph/paging

### 2. Add deterministic answer operators for common Intune questions

Current state: partially addressed. Stale managed-device sync questions now parse the day threshold, compute the cutoff from `generatedAt`, read matching `managedDevices` rows from SQLite by `lastSyncDateTime`, and include deterministic threshold/match metadata in the answer pack. Other precise predicates still need operators.

Why it matters: the example stale-sync answer duplicated a device and inferred dates. Adding `generatedAt` helps, but the model still should not be responsible for date arithmetic, dedupe, or threshold filtering.

Recommendation: continue adding deterministic query templates before the answer pack:

- stale managed devices: done for v0.2.2 first pass; live-pilot threshold/count validation still needed
- failed enrollment: use Autopilot events and enrollment failure report sources when Autopilot device identities fail
- compliance posture: group by `complianceState`, include explicit unknown/not evaluated counts
- assignments: use concrete policy/app/group relationships rather than generic text search

Evidence:
- `apps/desktop/electron/intune-chat/sqlite-store.ts` `readGraphRows()`
- `apps/desktop/electron/intune-chat/planner.ts` `buildAnswerPack()`

### 3. Treat Autopilot identity 500 as a known partial-source case

Live Lokka result: `/deviceManagement/windowsAutopilotDeviceIdentities?$top=1...` returned HTTP 500 from the Intune backend with `InternalServerError`, even with `DeviceManagementServiceConfig.Read.All` present.

Current state: partially addressed. Chat now plans and refreshes `/deviceManagement/autopilotEvents` for Autopilot/enrollment prompts. The source-specific identity failure remains visible through cache status/error metadata instead of being treated as a missing permission.

Remaining recommendation: add the enrollment failure report function after live validation, and make completed-message source details inspectable:

- `/reports/managedDeviceEnrollmentFailureDetails(...)` if the report function validates in the tenant

Live check: `/deviceManagement/autopilotEvents?$top=1...` returned successfully with an empty result set.

### 4. Strengthen hosted-provider pre-send consent

Current state: addressed in the worktree. Intune Chat now pauses before the first hosted-provider send per tenant/provider and explains the provider, model, tenant, data that leaves the device, and data that remains local. The admin can remember the decision on this device. The renderer sends a fresh acknowledgement for every hosted chat send, and Electron main/AppStateStore validates that it matches the active tenant/provider before chat persistence, cache refresh, or hosted LLM prompt construction.

Remaining work: decide whether remembered hosted-provider decisions should move from renderer `localStorage` into main-process state for stronger auditability. The current IPC acknowledgement prevents accidental/badly-shaped sends and enforces the host contract, but it is not a cryptographic proof against a fully compromised trusted renderer.

Evidence:
- `apps/desktop/src/pages/IntuneChat.tsx`
- `apps/desktop/electron/state.ts`
- `apps/desktop/electron/main.ts`
- `apps/desktop/electron/intune-chat/chat-service.test.ts`

## Priority 1 security and trust hardening

### 5. Enable renderer sandboxing or document the exact blocker

Current state: addressed in the worktree. The BrowserWindow now runs with `contextIsolation: true`, `nodeIntegration: false`, and `sandbox: true`. The preload moved to a CommonJS `.cts` module so Electron's sandboxed preload can expose the existing `window.openAdminOS` bridge without giving the renderer Node access.

Remaining work: keep future preload changes sandbox-compatible and add a packaged-app smoke check once signing/notarization work starts.

Evidence:
- `apps/desktop/electron/main.ts` BrowserWindow `webPreferences`
- `apps/desktop/electron/preload.cts`
- Electron security checklist recommends process sandboxing: https://www.electronjs.org/docs/latest/tutorial/security

### 6. Add runtime schemas for IPC payloads and validate sender frame

Current state: mostly addressed in the worktree. The preload exposes a narrow API, which is much better than exposing raw `ipcRenderer`. Current `ipcMain.handle()` callbacks now validate sender frame origin before privileged work. Intune Chat, Graph cache, provider/model selection, self-training, registry source changes, connectors, agent install/update/run controls, tenant selection, agent settings/schedules/delivery, draft-agent YAML flows, community submission metadata, external URL opening, and save-file requests now narrow renderer payloads with bounded strings, booleans, known enums, plain JSON object size caps, and targeted option-object validation before reaching the store.

Remaining work: extract these validators into reusable schema helpers once the IPC surface settles, and add focused tests for the validator layer itself rather than relying mostly on typecheck, host tests, and Electron smoke coverage.

Evidence:
- `apps/desktop/electron/preload.cts`
- `apps/desktop/electron/main.ts` `registerIpcHandlers()`
- Electron context isolation docs warn that IPC bridges still need argument filtering: https://www.electronjs.org/docs/latest/tutorial/context-isolation

### 7. Add CSP and stop loading remote fonts in the desktop app

Current state: addressed in the worktree. The desktop renderer no longer loads Google Fonts, the theme uses system UI and monospace stacks, and `apps/desktop/index.html` now declares a restrictive Content Security Policy. Renderer network access is limited to the app/dev origin plus loopback local-provider endpoints.

Remaining work: keep Graph, auth, registry, and hosted-provider calls in Electron main. If a future renderer-owned external connection is needed, document the reason and add the exact CSP origin instead of broadening `connect-src`.

Why it matters: this is not tenant-data telemetry, but remote font loads weaken the local-first story and CSP is part of the Electron security checklist.

Evidence:
- `apps/desktop/index.html`
- `apps/desktop/src/styles/globals.css`
- Electron security checklist recommends CSP: https://www.electronjs.org/docs/latest/tutorial/security

### 8. Sanitize subprocess environments for hosted CLI providers

Current state: addressed in the worktree. Codex CLI execution now runs with a minimal allowlisted environment instead of inheriting the desktop process environment. The allowlist keeps path, home/user, proxy, certificate, temp, locale, Windows shell path fields, and `CODEX_HOME`. It does not forward unrelated OpenAdminOS, Graph, Azure, or provider secrets. The CLI still runs in a temp dir with `--ephemeral`, `--skip-git-repo-check`, and read-only sandboxing.

Remaining work: verify on Windows after packaged signing work starts because `shell: true` depends on Windows shell/path behavior.

Evidence:
- `packages/runtime/src/llm-codex.ts`
- `packages/runtime/src/llm-codex.test.ts`

### 9. Detect non-loopback local provider endpoints

Current state: addressed in the worktree. Ollama endpoint trust is now classified before provider summaries are returned. Loopback and Unix-socket endpoints stay local; LAN, internet, wildcard, invalid, or otherwise non-loopback endpoints flip the Ollama provider to external/hosted-style trust messaging. Because existing Intune Chat consent logic keys off `provider.isLocal`, a non-loopback Ollama endpoint now requires confirmation before tenant context is sent.

Remaining work: add the same endpoint classification once LM Studio support lands.

Evidence:
- `packages/runtime/src/llm-ollama.ts`
- `packages/runtime/src/llm-ollama.test.ts`
- `apps/desktop/electron/state.ts`

### 10. Lock down registry source configuration

Current state: addressed in the worktree. Registry source URLs are validated and normalized before persistence. The host rejects empty/invalid URLs, credentials, query strings, fragments, `index.json` paths, non-HTTP(S) protocols, public HTTP sources, and private/localhost sources unless the explicit dev override is enabled. Switching away from the official registry requires a trust-review confirmation flag in the host contract. IPC now validates sender origin and bounds the URL payload before calling `setRegistrySource()`.

Cache identity is also pinned: cached registry indexes are reused only when their stored `sourceUrl` matches the current normalized source, preventing a failed custom source from silently showing agents fetched from another source. Settings now shows the active registry source in About readiness and exposes the editable source under Privacy with a product modal that explains the trust implication, host validation rules, and custom-source acknowledgement.

Remaining work: validate the Settings modal visually in packaged builds once the release installer flow exists.

Evidence:
- `apps/desktop/electron/state.ts` `setRegistrySource()`
- `apps/desktop/electron/registry-client.ts`
- `apps/desktop/electron/main.ts`
- `apps/desktop/electron/registry-client.test.ts`
- `apps/desktop/electron/registry-source.test.ts`
- `apps/desktop/src/pages/Settings.tsx`

## Priority 1 Graph, auth, and cache reliability

### 11. Reconsider initial consent bundle size

Current state: initial sign-in requests a broad read scope bundle so Intune Chat can work without repeated prompts. This matches the v0.2.2 direction, but the consent screen is heavy.

Recommendation: keep the one-consent option, but make it a deliberate feature choice:

- base tenant connection: identity, org, device basics
- "Enable Intune Chat cache": the full Intune/audit read bundle
- "Enable security/risky sign-in agents": P2/security read scopes

This keeps admins who only want a few agents from consenting to the entire chat surface.

Evidence:
- `packages/runtime/src/msal.ts` `DEFAULT_SCOPES`
- MSAL Node caching/persistence guidance: https://learn.microsoft.com/en-us/entra/msal/javascript/node/caching

### 12. Add Graph cache delta/incremental refresh where supported

Current state: scheduled refresh re-reads selected resources. For large tenants, full scheduled refreshes will be slow and more likely to throttle.

Recommendation: persist `@odata.deltaLink` for supported resources and use full scans only for unsupported endpoints or forced refreshes. Add backoff state per resource after repeated 429/5xx.

Evidence:
- `apps/desktop/electron/state.ts` `refreshDueGraphCaches()`
- Microsoft Graph delta query overview: https://learn.microsoft.com/en-us/graph/delta-query-overview
- Microsoft Graph throttling guidance: https://learn.microsoft.com/en-us/graph/throttling

### 13. Make Graph progress and errors inspectable after completion

Current state: addressed in the worktree. Progress is visible during chat, source pills remain compact, and completed assistant messages now include a `Source details` disclosure. Each used Graph resource shows cache/live status, row count, page count, cap state, refresh time, Graph path, selected fields, query parameters, and safe stored error text when available. New assistant messages persist the path/select/query metadata alongside the existing source row/page/freshness data.

Implemented shape:

- resource
- cache/live
- row count
- refreshed time
- query path and selected fields
- error body/request id when safe
- whether the result was first page only, full page set, delta, or capped

Remaining work: once Graph request IDs are captured from live errors, expose those IDs in the same disclosure. This helps admins trust or reject an answer without reading logs.

## Priority 1 UX and product flow

### 14. Promote Intune Chat earlier in onboarding

Current state: addressed in the worktree. Onboarding now ends with a workspace choice after tenant and provider setup: Intune Chat is the recommended primary action, Agent Hub is the repeatable-workflow path, and the first-agent install/run path is optional.

Implemented shape:

- Ask Intune Chat
- Browse/install agents

Avoid implying that installing/running a first agent is required before chat has value.

### 15. Add chat lifecycle controls

Current state: addressed for the v0.2.2 first pass. Intune Chat now has local
conversation search, pin/unpin, rename, delete, prompt edit/resend, Regenerate,
Stop, and local Markdown export controls. Search includes conversation titles
and message text through the SQLite store. Pinned conversations are grouped under
a collapsible Pinned section above Recent conversations in the history rail.
Delete uses a product modal and removes local conversation messages/tool-call
records without disconnecting the tenant or clearing Graph cache; conversation
rows also expose the delete path through a right-click context menu. Export
writes a local transcript with chat text and source metadata, not raw cached
Graph row payloads. Regenerate resubmits the preceding prompt through the normal
send path, and Stop aborts cancellable provider work and persists a `cancelled`
assistant entry instead of a partial generated answer. The Electron smoke
verifies Stop, Regenerate, pin, the pinned section, row context-menu delete,
rename, edit/resend, and source-details UI paths; host tests verify cancellation
persistence.

Remaining recommendation: future conversation branching/comparison would make
multiple regenerated answers easier to compare, but that is beyond the v0.2.2
first pass.

Current state: approved suggestions write local `self-training.yaml` and cannot add scopes or bypass confirmation. That is the right safety boundary.

Recommendation:

- show the exact YAML diff before acceptance

Evidence:
- `apps/desktop/electron/state.ts` `buildSelfTrainingYaml()`
- `apps/desktop/src/pages/Settings.tsx`

### 20. Expand learning signals beyond chat prompt text

Current state: suggestions are mostly based on explicit preference words in chat prompts and the top agent suggestion.

Recommendation: capture richer, still-local signals:

- rejected agent suggestions
- accepted/rejected write plans
