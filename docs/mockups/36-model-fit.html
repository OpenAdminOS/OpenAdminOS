Design reference 36

When the local model cannot do a request

Chat and agent runs say plainly why the model on this device cannot do this one request, in numbers when the provider gives them, and offer what else is configured. A hosted provider runs the request only after the admin chooses it and accepts a step that names where the data goes. The next message is back on the local model.

A. The notice: the request does not fit

Shown in place of the generic error when the local model rejects a request for its size. Nothing has gone to another provider yet. The choices list only providers that are configured and ready, with no default: every option is a separate button, none is focused or highlighted.

  • Numbers come from the provider's error (Ollama names both) or, once it lands, from the runtime's prompt fit check. Without numbers: "This request is larger than the context OpenAdmin 8B is set to."
  • Hosted rows always show the production location label in amber, and a cost note: the app does not know the admin's plan or price, so it says where the cost lands.
  • The larger local model is chosen by the size in its name (8B, 20B). Its context window is not read, so the note says so.
  • Split the question puts the question back into the composer with a hint. Nothing is split automatically.

B. Accept step

Choosing Claude Code opens the hosted confirmation in its per-request form, above the composer. It names the provider and where the data goes, says it is for this request only, and has no remember box. Enter does not send from here: only the Send button does.

F. Agent run that does not fit

A run that fails because its prompt is larger than the local model's context offers the same choices on the run page. Choosing a provider opens the run review, which is the accept step for runs: it names the provider, where prompts go, and why this provider is used for this run only. A write agent still stops at the diff and its typed confirmation.
