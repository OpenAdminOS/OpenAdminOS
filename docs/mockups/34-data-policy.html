Data policy decides what each model may see, and every answer says what was hidden.

Six data classes, three provider tiers, three actions. Rules apply on this device before every model call: agent runs, Chat, Office, drafts, follow-ups and Nova. A masked value is replaced by a token for the call and restored on the way back, so the admin reads real names while a hosted model sees placeholders. Check the frames at 1280 and 900 px, in both themes. Click any cell in A to change a rule; the sample line redraws.

Open questions

Decisions this mockup assumes but does not make. Each one changes copy or a screen above.

  1. Token format. The preview shows [DEVICE_1], [USER_1] and [CREDENTIAL]. The model sees whatever format is chosen, and so does the admin in this preview. Is a typed, numbered bracket the format?
  2. Classifying fields. F lets the admin classify an unmapped field, including into a looser class after a dialog. Should that be allowed, limited to stricter classes, or left to IT and to mappings shipped with the app?
  3. Confidential column before Track C. A shows it with "No provider qualifies yet". The alternative is to hide the column until a provider can be confidential, which makes the first release simpler and the later change bigger.
  4. What the counts count. C and D count values replaced. Counting distinct people and devices reads better ("4 devices, 4 people") but needs the app to group values per object.
  5. Per organization. The mockup has one policy for the device. Should an organization be able to carry its own rules, for example stricter ones for a customer tenant an MSP manages?
  6. Block on Local. The plan lets the admin tighten any rule, so Block is pressable in the Local column. Is there a real case for it, or should the local column offer Allow and Mask only?
