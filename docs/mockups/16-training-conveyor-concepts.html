The training line, as a factory

Four visual directions for a live status page at training.openadminos.com. All of them show the same thing: a side view of the OpenAdmin training pipeline as an animated conveyor belt, one machine per pipeline stage. The stage highlight, the log line and the counters below each scene are simulated here; in production the rented GPU pod posts run state to an API and the page renders it.

The seven stations map 1:1 to the real pipeline in model/, including the honest parts: the validator visibly bins rejected samples, and the review station can hold a run instead of shipping it (as happened with r5).

How any of these becomes a live page

The scene is static art; only three things change at runtime, which keeps the API tiny. The pod pipeline scripts in model/train/ gain one curl call per stage transition:

POST /api/run/state        { run: "r7", stage: "train", detail: "step 1240/3000 · loss 0.83" }
GET  /api/run/state        → page polls (or SSE) and: highlights the station,
                             updates the log line, advances the belt widgets
GET  /public-data.json     → everything historical: scores, suites, run log

Everything below the belt (chips, log, counters) renders straight from that state plus the existing model/site/public-data.json contract, so the page can never claim more than the pipeline actually reported. When no run is active, the line idles and the page shows the last released version and its scores.

Open questions flagged for you rather than decided here: whether the page shows failed and held runs on the belt itself (I would, it is the whole trust pitch), and whether concept 2 or 4 fits the "no hype" brand rule or should stay a social-preview asset only.
