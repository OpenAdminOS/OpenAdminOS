# v0.4 UX simplification, round 2 — one obvious surface

**Status: implemented; release evidence pending.** Refined with Claude Code Fable. The Phase 0 decisions are recorded in `docs/SPEC.md`; platform checks and external administrator sessions remain before release.

**Interactive visual reference:** `docs/mockups/13-v0.4-one-surface.html` demonstrates the proposed Chat front door, route-aware single rail, progressive context controls, searchable Settings, and outcome-first Agents. It is a review artifact, not approval of the Phase 0 decisions.

**Post-implementation usability correction (2026-08-06):** Home was removed rather than retained, `/` redirects to `/chat`, Settings now sits in the primary navigation group, issue reporting lives in Settings → About and contextual recovery, and constrained-width Chat uses a full-text overlay history drawer instead of a numbered mini-rail. These decisions supersede the earlier Home and compact-rail references below.

## Target experience

OpenAdminOS opens in Chat with the composer ready. One stable rail uses a familiar desktop hierarchy: brand and active tenant first, then Chat, Agents, Changes, and Settings as one primary navigation group. Route-specific context stays inside the active workspace. The empty state asks one question and offers no more than three examples. Tenant and provider context remain visible, but detailed trust copy appears at the decision boundary where it matters. Advanced scope, saved-query, and workspace controls stay available behind progressive disclosure.

A new Microsoft 365 admin should reach a useful tenant answer in under five minutes without first learning the product's internal taxonomy.

## Non-negotiable constraints

- Local-provider tenant data and prompts never leave the device.
- Hosted-provider egress names the provider and requires the existing confirmation where applicable.
- Every write pauses for diff confirmation. Destructive writes retain typed confirmation.
- No agent starts without an active tenant, and the active tenant remains visible at all times.
- Every failure has a specific recovery path.
- The Electron desktop app remains the only end-user surface.
- Do not introduce Full access defaults, multi-surface architecture, or hover-only critical actions.
- Avoid backend rewrites unless routing needs a narrow existing-contract extension.
- Do not add tenant-content, prompt, result, error-payload, or first-result telemetry.

## Phase 0 — Approve and record the product decisions

The current SPEC section 4a locks Home at / and places the first-run checklist there, while also saying that Chat is the front door. Code must not change this silently.

### Decisions requiring approval

1. **Landing route:** approve / redirecting to /chat and remove the redundant Home surface.
2. **First-run guidance:** render compact readiness guidance in Chat until the first successful answer or run.
3. **Single rail:** use one stable outer rail with Chat, Agents, Changes, and Settings grouped directly below the active tenant; keep route-aware context inside the active workspace and do not retain a second icon rail.
4. **Home:** remove it; existing canonical Chat, Agents, Changes, run-history, and status surfaces already contain its useful information.
5. **Examples:** use three fixed editorial prompts—devices, apps, and security—rather than rotating suggestions.
6. **Usability gate:** require 3–5 external Intune-admin sessions before tagging v0.4.0.

### Files

- docs/SPEC.md — section 4a addendum after approval
- tasks/todo.md — active-roadmap pointer
- CHANGELOG.md — implementation entries as phases land

### Acceptance criteria

- The six decisions above are approved or explicitly amended.
- SPEC section 4a is updated before behavior-changing work begins.
- The checklist success signal remains unchanged: one completed assistant response or completed run.

## Phase 2 — Make conversations and Settings URL-addressable

### Rationale

Selected conversations and Settings sections currently live in component state. URLs should restore state across reload, back/forward navigation, notifications, and command-palette actions.

### Route model

- / redirects to /chat
- /chat is a new draft
- /chat/:conversationId restores a persisted conversation
- / redirects to /chat; there is no dashboard route
- /settings redirects to /settings/providers
- /settings/:section opens a validated section
- Existing /hub and other compatibility redirects remain

## Phase 3 — Use one contextual rail

### Rationale

Chat and Settings currently show two full left rails. The contextual rail must replace the global rail, not sit beside it.

### Rail modes

- **Persistent frame:** brand and active tenant/switcher stay at the top; Chat, Agents, Changes, and Settings stay together directly below the tenant.
- **Chat middle context:** New conversation and pinned/recent conversations; conversation search appears only when the list requires it.
- **Settings middle context:** Settings search and Settings sections.
- **Agents, Changes, and Run Result middle context:** empty by default; add route-specific controls only when they provide real value.

### Acceptance criteria

## Phase 5 — Deduplicate trust messaging and flatten visual density

### Rationale

Trust text currently competes across the StatusStrip, header, composer, Home, and cards. Repetition encourages users to ignore it.

### Rules

- StatusStrip is the canonical persistent tenant/provider/local-or-hosted line.
- Full trust copy remains at hosted send, multi-tenant scope review, write confirmation, connector confirmation, and onboarding.
- Local/no-attachment Chat needs no duplicate composer sentence.
- Hosted or attached-context Chat keeps a concise boundary line.
- Maximum two bordered container layers in a region.
- Pills communicate state only: Read-only, Write, Local, Hosted, Connected, Warning, Failure.
- Preserve the restrained orange accent, mono metadata, and terminal-adjacent tone.

### Likely files

- apps/desktop/src/components/StatusStrip.tsx
- apps/desktop/src/components/Card.tsx
- apps/desktop/src/components/Pill.tsx

- apps/desktop/src/pages/settings/
- apps/desktop/src/styles/globals.css

### Acceptance criteria

- Local Chat has exactly one persistent trust line.
- Hosted mode names the provider at the composer boundary and confirmation modal.
- Active tenant remains persistently visible.
- No screen contains three nested bordered containers.
- Before/after screenshot review approves the density change.

## Phase 9 — Usability validation and release gate

### Moderated protocol

Recruit 3–5 external Intune administrators. Use a clean, preconfigured test tenant/provider state and ask them to:

1. Ask a tenant question and obtain an answer.
2. Determine why a device is noncompliant.
3. Run a read-only agent.
4. Find that run again.
5. Change or inspect the active provider.

Record task completion, time to first useful result, hesitation points, errors, and whether the participant can state the active tenant and local/hosted data boundary. Do not ship or upload timing telemetry.

### Release acceptance criteria

- At least three sessions completed.
- Median time to first useful result is under five minutes.
- No task-blocking finding remains open.
- Trust and write-safety comprehension succeeds in every session or is fixed before release.

### Final verification

- npm run typecheck
- npm test
- npm run qa
- npm run build
- npm run smoke:intune-chat under xvfb
- npm run smoke:report-issue under xvfb
- npm run screenshots with refreshed desktop and narrow-window captures
- npm run docs:check
- Score `v0.4-quality-gap-closure.md` with automated, visual, platform, and external-session evidence attached
- Manual real-desktop pass: keyboard-only Chat, reduced motion, 900px window, hosted consent, multi-tenant scope review, and destructive typed confirmation
- CI fully terminal and green on the final PR head before reporting release readiness

## Migration and backward compatibility

- Conversation ids and SQLite data remain unchanged; routing reads existing ids.
- /, /settings, and /hub retain redirects for stale internal links.
- Electron menu, tray, notification, smoke, and screenshot targets change in the same commit as routing.
- Remembered hosted consent remains keyed by tenant and provider and is route-independent.
- New rail/disclosure preferences are additive local UI preferences; missing values use defaults.
- No Graph endpoint, scope, or write contract changes are part of this plan.
